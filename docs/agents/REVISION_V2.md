## Product rules (v2) — implement these, nothing contradicting them
1. **Booked ≠ demo-ready.** Demo-ready = confirmed need/use case (customer statement with evidence) AND a demo objective agreed with evidence (`objectiveStatus === 'agreed'`). Budget, authority and timing may stay open. Code enforces `demoReady = needConfirmed && handoff?.objectiveStatus === 'agreed'`, whatever the model says.
2. **Unknown is not No.** Missing budget/role/timing never lowers fit or priority; it becomes an open BANT item + a question. Only evidenced statements change a dimension. No fit penalty for an unqualified booking. `fitScore`/`interestScore` stay internal; the UI shows Priority (Hoch/Mittel/Niedrig/Prüfen) + one-sentence reason + three dimensions (Fit, Grund/Timing, Bedarf/Gesprächsbereitschaft) + BANT completeness separately.
3. **Priority** (lib/priority.ts): High = fitting company + current specific expressed need OR an agreed request to talk (unknown role → stays High with a clarification task "Rolle klären"); Medium = fitting company + evidenced relevant reason but need not confirmed; Low = only weak contact signals (like, accepted connection, open/click) or insufficient context; Review = interest from outside the ICP or a significant unresolved contradiction (separate queue, never mixed into the regular list). Opt-out/exclusion → stopped, never prioritized. Agreed conversations first.
4. **Triggers**: catalog types now include "Geäußerter Bedarf" (expressed need, evidence = chat/call statement) and "Ausdrücklicher Gesprächswunsch". Gates: catalog match (else candidate), evidence (public URL+date OR chat/call excerpt with time), recency (event date ≠ retrieval date; stale → `isActive=false`). Relevance 0–3 each with a reason. NO automatic upgrade for two triggers. Unsupported/contradicted/stale → not an active call reason (keep row, `isActive=false`, record why). Intrusive/sensitive → never in the opener.
5. **Brief**: context, evidenced reason, opener (never presents a hypothesis as a customer statement), facts / hypotheses / open questions kept apart, BANT status per dimension (confirmed/assumed/open + evidence), at most 3 prioritized open questions, optional ≤3 talking points, ≤2 objection answers ONLY from `campaign.offerKnowledge` (else "Offene Frage: …" instead of a promise), consent line, meeting slots labeled "Vorschlag – Verfügbarkeit bestätigen". Uses existing chats (`lead_context`).
6. **After the call** (notes and/or pasted transcript): conversation score (8 criteria, 0–2, null = not observed; listening = builds on answers, not talk share; objection only scored if one occurred). Display "9/12 · 6 von 8 bewertbar". Coaching = one strength + one improvement + alternative sentence. BANT updates with evidence → `bant_claim` rows (source 'call', `call_log_id`). Trigger feedback per active trigger: confirmed / contradicted / not_tested — only confirmed/contradicted need evidence; not_tested must not degrade the trigger. Lead corrections only with evidence (wrong person → correct role + contact route, don't downgrade company). Recommended action: demo_handoff | follow_up | identify_contact | stop | research. Demo handoff (if need confirmed or demo agreed): company/ICP, known participants, use case + evidence, BANT, demo objective + status, demo suggestion (marked as system suggestion), next action, open questions.
7. **Seller override**: seller may change the action with an optional reason → stored in `call_log.seller_action/seller_reason`; never changes demo-ready/BANT status; no "system wrong" label.
8. **Campaign proposals**: only from ≥ `campaign.minSampleSize` comparable cases (same trigger type with confirmed/contradicted feedback); show assessed count / denominator, evidence, uncertainty, old and new rule; status proposed until a human approves; approving applies the change to `trigger_catalog` (e.g. tier/approved); individual cases only correct the lead.
9. Slack, calendar, warm-up = secondary; keep working but don't extend.

## API contracts (new/changed) — implement and consume exactly
- `computePriority(input: { lead: Lead; triggers: LeadTrigger[]; context: LeadContext[]; bant: BantClaim[]; campaign: Campaign | null }): PriorityResult` — pure, in `lib/priority.ts` (owner D).
- `refreshLeadPriority(leadId: string): Promise<PriorityResult>` — in `lib/priority.ts`: loads lead, triggers, context, bant, active campaign via getDb, computes, writes priority/priority_reason/fit_status/need_status/willingness to the lead row (owner D). Callers: outcome route, pipeline, research route, seed.
- `POST /api/leads/[id]/outcome` body `{ outcome: CallOutcome; notes?: string; transcript?: string }` → `{ callLog: CallLog; evaluation: CallEvaluation | null; priority: PriorityResult }` (owner A).
- `POST /api/leads/[id]/override` body `{ callLogId: string; action: NextAction; reason?: string }` → `{ callLog: CallLog }` (owner D).
- `GET /api/proposals` → `{ proposals: CampaignProposal[] }`; `POST /api/proposals` (compute from trigger feedback) → `{ proposals: CampaignProposal[]; message: string }` (German, e.g. "Noch zu wenige vergleichbare Fälle (2 von 3)."); `POST /api/proposals/[id]` body `{ decision: 'approved' | 'rejected' }` → `{ proposal: CampaignProposal }` (owner D).
- `GET/POST /api/campaign` additionally carry `offerKnowledge`, `minSampleSize` (owner D).
- Mappers for every new table/field in `lib/mappers.ts` (owner D, do this FIRST — others import `toLeadContext`, `toBantClaim`, `toCampaignProposal`, and the extended `toLead`, `toLeadTrigger`, `toCallLog`, `toCampaign`).
